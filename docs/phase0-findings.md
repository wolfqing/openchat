# Phase 0 结论：评论与 issue 分析

**日期**：2026-10-28
**范围**：路线图 Phase 0 第一项（App Store 评论 + GitHub issues）。真机实测、Android 许可证路线和定名尚未做。

## 一句话结论

按路线图预先写下的 kill 条件，**前提 1 不成立**：UX 类抱怨在差评和 issue 里都只占约两成，是少数。用户最大的痛点是「消息收不到」和「附近没人」，这两件事换一个界面解决不了。但「上游不会重做面向普通人的界面」这一点得到了证实，所以结论是：**Phase 1 按原计划不启动**，先用真机实测决定是放弃还是换前提。

## 关键发现

- **用户先卡在「收不到」，不是「看不懂」。** 最常见的差评是 App 进后台后收不到消息、iPhone 和 Android 互发图片失败、两台手机挨着也连不上。iOS 后台蓝牙受系统限制，前端重做绕不过去。
- **「附近没人」是第二大抱怨。** 有人在大城市市中心和机场也没见过一个用户。这直接削弱前提 3：协议兼容确实能接上现有网络，但现有网络本身大部分时间是空的。
- **说「好用」的不少于说「难用」的。** 有 6 条评论主动夸简单直观，其中一条说祖母 15 分钟能学会。纯 UX 抱怨只有 11 条。
- **写评论的人偏技术。** 不少 UX 抱怨反而是 IRC 用户在说 `/join`、`/j` 命令失效。2025-07 上线那一波占了评论的大头，主要是加密圈和技术圈的早期用户。
- **上游 iOS 明确不做大众化界面。** iOS 维护者在 issue #1481 里拒绝了 messenger 式重设计，称终端风格是刻意的身份选择，并说不同客户端可以在这里分化。「启动先进会话列表」的 PR #1364 在 2026-10-25 被关闭，未合并，新用户仍然直接落在公开的 #mesh 频道。
- **Android 端已经在往大众化走。** 消息样式和品牌刷新的 PR #767 已于 2026-07 合并，v2.1.0 也改了 onboarding 布局。openchat 的界面差异化只在 iOS 上还成立。
- **法国这一波没有 UX 信号。** 2026-10-17 之后的 8 条法国评论里，有 2 条怀疑 App 被政府监控，抱怨垃圾信息和通知各 1 条，界面问题 1 条。

## 三条前提的判定

| 前提 | 判定 | 依据 |
|---|---|---|
| 1. 普通人用不明白，现有界面留不住他们 | 不成立，证据偏弱 | UX 占抱怨约 19%，触发 kill 条件。但不会写评论的人卸载了也不会留下记录 |
| 2. 基础设施故障场景足够大，且能留在商店 | 未检验 | 本次数据不涉及 |
| 3. 协议兼容就没有冷启动问题 | 被削弱 | 「附近没人」占抱怨 28% |

## 更正

仓库原先写着「上游没有完成过第三方审计」，这是错的。Android 维护者在 2026-01 按「Cure53 Audit BCH-01（2025-11）」提交了 9 条问题，其中 3 条为高危。截至 2026-10-28，高危的冒充问题 #589 和中危的重放问题 #593 仍未关闭。审计报告原文在两个仓库里都没找到。另外，上游 iOS README 已经删掉了「未经安全审查、勿依赖」的警示。协议笔记和两份 README 已同步更正。

## 下一步

1. **做完 Phase 0 的真机实测再定生死。** 评论样本有幸存者偏差，看不懂就卸载的人不会留言。找三个非技术用户，在飞行模式下从安装到发出第一条消息，记录步数、秒数和卡住的位置。如果三个人都能顺利发出，就关闭项目。
2. **如果实测发现明显卡点，就换一个前提，而不是照原计划做。** 数据支持的方向是「预先约好的一群人」场景，比如活动、徒步队、防灾演练。这类场景的密度靠组织来保证，不靠路人，能同时绕开「附近没人」和冷启动。
3. **Reddit 和印度两块没有数据。** r/bitchat 的接口和网页都被拦截。印度区 App Store 已下架，查不到评论。

## 方法与局限

- 评论来自 Apple 公开的评论 RSS，每个国家最多 500 条。只有带文字的评论会出现在里面，美国区 520 个评分只拿到 84 条。
- 183 条评论逐条人工打标签。764 条 issue 先用关键词规则分类，再按标题人工修正 177 条。灌水和无效 issue 58 条不计入分母。
- 原始数据、标签表和脚本在 `internal/phase0/`，该目录不进 git。
